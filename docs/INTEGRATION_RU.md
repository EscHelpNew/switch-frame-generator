# Подключение LSFG к игре на Nintendo Switch

Статус: host-подготовка и сборка ARM64 NRO проверены. Аппаратная проверка пока
не выполнена; подробные результаты находятся в [VALIDATION.md](VALIDATION.md).

## Что получает генератор

LSFG использует последовательность готовых изображений сцены. Он оценивает
движение сам: глубина, физика, игровая логика и векторы движения движка не нужны.
Нужны доступ к GPU-изображению и управление очередью вывода. Наш адаптер работает
с deko3d на первой Switch. Это библиотека внутри приложения, а не перехватчик
экрана произвольной игры.

Генерация 2x означает один промежуточный кадр между двумя исходными. Это
не предсказание будущего: B должен быть готов до показа mid(A,B). Минимальная
задержка и итоговый FPS зависят от очереди вывода, GPU и частоты исходного рендера.

## Подготовка на ПК

Положите собственную `Lossless.dll` в корень проекта. Она исключена из Git.
Сборка host-инструмента использует закреплённые версии SPIRV-Cross и форка UAM:
обычный `uam.exe` из SDK используется только для собственных шейдеров сцены.

Точка входа сборки — `py -3 build.py` (native Windows Python). Она собирает host-инструмент,
извлекает SPIR-V, переводит его в GLSL, компилирует DKSH и проверяет кэш повторным
чтением. В NRO включается локальный кэш через romfs. DLL на Switch не исполняется.
Варианты DLL могут отличаться: при ошибке распознавания или компиляции сборка
должна остановиться, а не подменять LSFG простым смешиванием.

## API адаптера

Интерфейс реализации находится в `include/sfg/generator.hpp`:

```cpp
auto generator = sfg::Generator::create(
    device, width, height, cache_directory, error);
if (!generator) {
    std::fprintf(stderr, "LSFG disabled: %s\n", error.c_str());
    // Оставить обычный рендерер; не обращаться к input()/record().
} else {
    const DkImage* target = generator->input();
    // Записать рендер сцены в target без HUD.
    const DkImage* generated = nullptr;
    const DkImage* original = nullptr;
    if (!generator->record(cmd, generated, original, error)) {
        // Не отправлять неполный список команд. Дождаться ранее отправленной
        // GPU-работы, отключить этот экземпляр и перейти на обычный рендерер.
    }
}
```

Создание загружает и проверяет кэш, заранее выделяет текстуры, shader code,
descriptors и uniform buffers. Очередью и временем жизни command buffers владеет
игра. `record()` только записывает GPU-команды: не ждёт GPU, не делает submit
или present. Полученные указатели принадлежат генератору; не освобождать их.

Точные сигнатуры:

```cpp
std::unique_ptr<sfg::Generator> sfg::Generator::create(
    DkDevice device, unsigned width, unsigned height,
    const char* cache_directory, std::string& error);
const DkImage* sfg::Generator::input() const;
bool sfg::Generator::record(DkCmdBuf cmd, const DkImage*& generated,
    const DkImage*& original, std::string& error, float alpha = 0.5f);
void sfg::Generator::reset();
```

В этом стенде рендер, обработка и вывод всегда **1280×720** по требованию
пользователя. Эксперимент 640×360 не принят выбранной схемой ресурсов при flow
1/4 и не включён в демо. Для другой игры библиотека принимает размеры явно,
но их необходимо проверить через backend::accept и тестировать отдельно.

## Какие файлы добавить в сборку игры

Подключить `include/`, `third_party/drastic/third_party/lsfg-deko3d/include/` и
заголовки libnx/deko3d. Скомпилировать `source/generator.cpp` и следующие файлы
из `third_party/drastic/third_party/lsfg-deko3d/src/`:

```text
binding.cpp        cache_format.cpp   cache_load.cpp    cache_store.cpp
dksh.cpp           error.cpp          image_graph.cpp   layout.cpp
pe_resources.cpp   schedule.cpp       sha256.cpp        shader_set.cpp
spirv_module.cpp
```

Использовать C++20, exceptions, стандартный Switch toolchain и библиотеки
`deko3d` (либо debug `deko3dd`), `nx`, `m`, стандартную C++ runtime.
Пример проверенных флагов и линковки находится в `build.py::target_build`.
Не включать `prepare.cpp`, `translate.cpp`, `compile_uam.cpp`, UAM или
SPIRV-Cross в исполняемый код игры: они нужны только на ПК.

После `py -3 build.py --host-only` имя выбранного кэша находится в
`build/cache/selected.txt`. Скопировать `manifest.bin` и **все 25 файлов
00.dksh..24.dksh** из соответствующей папки в romfs игры, например `lsfg/`.
Указать `--romfsdir` при вызове elf2nro и вызвать `romfsInit()` до create.
В этом примере cache_directory равен `romfs:/lsfg`. При другом имени папки
передать фактический путь. Можно хранить тот же проверенный кэш на SD.

Для собственного renderer `main.cpp` и шейдеры мяча не нужны. Если shader code,
scene color или очередь живут в другом модуле игры, передать их через API:
не создавать второй deko device ради генератора.

Очередь должна поддерживать Graphics и Compute. В демо установлен
`DkQueueMaker::perWarpScratchMemorySize = 65536`; фактически выбранные шейдеры
прошли host-проверку с максимумом 2048 байт scratch/warp. Сохранять запас
при смене DLL/режима; runtime отклоняет больше 65536. Размер реального LSFG
image pool при 720p в recording-проверке — 11 MiB; аппаратный layout и общий
расход памяти нужно подтвердить на Switch. Лимит pool — 192 MiB.

## Где подключать в существующем рендерере

1. После создания deko3d device и compute-capable queue создать генератор
   под фактическое разрешение исходной сцены, не разрешение экрана после upscale.
2. Вместо непосредственного рендера в swapchain привязать `input()` как color
   render target. Если игра уже использует offscreen color image, скопировать
   итоговую сцену в `input()` совместимой GPU-копией до `record()`.
3. `input()` меняется с history phase: получать его заново перед каждым исходным
   кадром. Повторные показы одного кадра не должны вызывать `record()` снова.
4. Вызвать `record()` после завершения записи сцены. Адаптер устанавливает
   barriers render→compute и compute→последующий потребитель в той же очереди.
5. Скопировать/масштабировать возвращённое изображение в приобретённый swapchain
   image, затем нарисовать HUD, меню, прицел и текст. LSFG меняет descriptor sets,
   compute shaders и bindings; перед собственными проходами восстановить нужное
   состояние. Не считать его сохранённым автоматически.
6. Отправить команды и показывать результаты с периодом дисплея. CPU не должен
   перезаписывать command/uniform/timestamp memory, пока GPU её использует.

## Порядок вывода 30→60

Устоявшаяся последовательность: `A → mid(A,B) → B → mid(B,C) → C`.
Обработка B возвращает `generated=mid(A,B)` и `original=B`. Показывайте
generated, затем original, сохраняя интервалы примерно 16,67 мс на 60 Гц.
Первый реальный кадр показывается как warmup; его можно повторить на втором
такте дисплея. Пока `generated == nullptr`, история ещё прогревается:
показывать только реальные изображения.

Не показывать B перед mid(A,B), не вызывать физику второй раз ради generated
и не принимать два быстрых вызова present за доказанные 60 FPS. Если бюджет
превышен, фиксировать пропуск deadline и показывать актуальный реальный кадр
по явно выбранной политике; не накапливать неограниченную очередь старых кадров.

Симуляция может работать чаще 30 Гц. Ограничение здесь относится к исходному
рендеру сцены. Демо использует одинаковую фиксированную физику во всех режимах.

## Сброс и завершение

`generator->reset()` требуется после перемотки, загрузки, camera cut, сброса
сцены и перехода между режимами. Reset инвалидирует историю; первые результаты
после него идут через warmup. При смене разрешения дождаться GPU, уничтожить
генератор и создать новый с нужными размерами. Историю разного размера не смешивать.

Перед уничтожением генератора, связанных image views/descriptors, command memory
или device выполнить `dkQueueWaitIdle(queue)` либо эквивалентно дождаться всех
использующих их fences. Сначала завершить GPU-работу, затем освободить генератор,
потом очередь/device. При ошибке и выходе соблюдать тот же порядок.

## Переменный источник 20–30 FPS → цель 40 FPS

Новый общий планировщик находится в `include/sfg/frame_pacer.hpp`; он не зависит
от OpenGL и пригоден для Switch. Цель — слот раз в 25 мс, максимум один generated
на пару реальных кадров. В библиотеке `record(..., error, alpha)` задаёт время
промежуточного кадра между A и B: строго `0 < alpha < 1`; по умолчанию 0,5.
Изменение записывается GPU-командой с barriers, без небезопасной записи CPU
в uniform buffer, который ещё может использовать GPU.

```cpp
sfg::FramePacer pacer(40);
// Один раз после первого реального кадра:
auto initial = pacer.start(first_timestamp_seconds);
// Для каждого последующего реального кадра с возрастающим timestamp:
sfg::PairPlan plan = pacer.push(current_timestamp_seconds);
float alpha = 0.5f;
for (unsigned i = 0; i < plan.count; ++i)
    if (plan.samples[i].kind == sfg::SampleKind::generated)
        alpha = float(plan.samples[i].alpha);
// После записи сцены в input():
bool valid = generator->record(cmd, generated, original, error, alpha);
```

Проверки результата `create()`/`record()` и warmup остаются обязательными.
Для каждого sample скопировать выбранное изображение в собственную ограниченную
очередь: `real` — текущий original, `generated` — generated при готовой истории,
`repeat` — прошлый реальный кадр. В планировщике при длинном разрыве FG стоит
непосредственно перед новым real, поэтому после него не повторяется более старый A.
Во время warmup запрошенный generated заменяется явно учитываемым повтором.

Хранить указатель на history/generated для отложенного показа недостаточно:
следующий реальный кадр перезапишет эти текстуры. Нужна GPU-копия в отдельные
слоты с корректными barriers/fences. В PC-примере выделено 12 слотов и
используется целевой буфер 75 мс; передача на показ начинается на 8 мс раньше
слота, оставляя запас драйверу. Это добавляет задержку и требует отдельного
измерения на целевой платформе. Данные очереди могут быть другим форматом/размером
только после подтверждения совместимости GPU-copy.

Текущий вариант выполняет LSFG на каждом исходном кадре для сохранения временной
истории, даже когда план не использует результат. Не пропускать произвольные
проходы только по числу запрошенных показов: это нарушит внутреннюю историю.
При FPS ниже 20 одного generated на реальный не хватает для 40 уникальных:
показывать явно учтённые повторы, не увеличивать скрыто multiplier.

Вывод должен жить по собственным deadline, отдельно от прихода источника.
При долгой задержке пропускать просроченные исходные отсчёты и кадры очереди;
не воспроизводить бесконечный backlog. Native Switch-демо сохраняет исходные
фиксированные режимы; адаптивный планировщик сейчас аппаратно проверен на ПК.

Для реакции на ввод: опрашивать его между показами; при резком изменении сцены
обработать событие движком, сбросить stale queue/history и подготовить новый real.
В превью попадание клика проверяется по позиции именно показанного мяча;
переход может дать повторы до восстановления истории. LSFG сам не интерпретирует
кнопки и не предсказывает новую физику без нового входного изображения.

## Если игра использует NVN, OpenGL или Vulkan

`DkImage*` не является переносимым handle. Нельзя привести NVN texture или
VkImage к DkImage. Нужен адаптер sharing/import с подтверждёнными layout,
format, memory ownership и межочередной синхронизацией, либо исполнение LSFG
на родном API игры. Сам алгоритм без данных движка работает, но работа с
его GPU-буферами всё равно требует интеграции.

Универсальный вариант для готовых игр — отдельное исследование перехвата present
и владения буферами, вероятно как внедряемый модуль/системная служба. Обычный
netloaded NRO этот доступ не получает. Поток SysDVR тоже не даёт механизма
вставки изображений обратно в очередь экрана консоли.

## Проверка в своей игре

Сначала проверить обычный рендер, затем LSFG на той же сцене и штатных частотах.
Писать отдельно CPU submission time, GPU scene time, GPU LSFG time, исходный FPS,
generated count и интервалы вызова present. Счётчики present не подтверждают
фактический scanout: визуально проверить отскоки/быстрое движение и cadence.
HUD должен оставаться резким, camera cut не должен давать кадр из старой сцены.

Изолированный мяч — проверка пути обработки, не прогноз скорости тяжёлой игры:
LSFG конкурирует с ней за тот же GPU и пропускную способность памяти.

## Netloader

Для первого запуска открыть hbmenu в application mode, нажать Y и передать NRO
через `nxlink -s -a <IP> <путь-к-NRO>`. Один процесс на ПК принимает nxlink logs.
Трей Switch Monitor только наблюдает за службами и не является netloader.

Перезапуск без возврата в netloader через Switch Debug Kit требует отдельного
подключения receiver и собственного установленного forwarder. Не использовать
ProgramId, bridge.nro или ключи другого приложения. Этот этап не нужен для
первой проверки LSFG.
